F10. 前月予定の複製
目的
前月のイベントを次月の下書きとして安全に複製し、手入力を減らします。
MVP 1.0での推奨仕様
* 複製元は対象月の前月に限定する。
* 対象月は1か月分に限定する。
* 作成状態はDRAFT。
* PDFは複製しない。
* LINE通知は作成しない。
* firstPublishedAt = null。
* readRequiredAt = null。
* 既読、個人メモ、LINE履歴は複製しない。
* 作成者・更新者は複製を実行したMembershipにする。
* 日付はクラブtimezone上で1か月進める。
* 存在しない月末日は対象月末へ丸める。
* 実行前に複製予定をpreviewする。
* 1回の最大件数は100件とする。
* 同じrequestIdの再送信は1回だけ処理する。
実装範囲
1. 一括操作用の冪等性モデルを追加する。
    * 例：ClubEventBatchOperation
    * clubId + requestIdをuniqueにする。
    * operation種別、input hash、実行者、作成件数、完了日時を保存する。
2. 前月イベントをclubId付きで取得する。
3. 変換後日時をclub timezoneで計算する。
4. preview画面で対象・除外・日付補正を表示する。
5. 完全一致する既存イベントは重複候補として表示し、初期状態では除外する。
6. 1 transactionでBatchOperationとイベント群を作る。
7. 添付・通知・既読等を作らないことをテストする。
8. 管理者月別一覧から導線を追加する。
受入条件
* 別クラブのイベントは複製できない。
* 二重送信でも同じイベント群が増えない。
* 1月31日から2月への変換等、月末補正がtimezone込みで正しい。
* 生成イベントはすべてDRAFTで、PDF・LINE・既読情報を持たない。
* 100件超は実行前に拒否する。
理解する重要箇所
* 一括作成ではUIのpendingだけでなくサーバー冪等性が必要なこと
* UTCではなくclub timezoneの日付を先に変換する理由
* 一般的な定期イベント複製はMVP 1.5へ残すこと


【追加：粒度1】仕様・入力・結果の契約

ユーザー確定事項
* 複製元は、クラブ現地時刻で対象月の前月に開始したイベントだけとする。
  前々月に開始し、前月にも継続している予定は含めない。
* 完全一致は、変換後のコピー対象項目で比較する。
  既存側のDRAFT／PUBLISHEDは問わず、作成者・更新者・公開日時・PDF等は比較しない。
* 除外前の前月候補が101件以上なら、preview段階で拒否する。
  日付不正や重複の除外、選択件数の削減によって上限を回避しない。

粒度1で定義する入力境界
* 対象月は、前月も西暦1年以上となる単一のYYYY-MM文字列とする。
  0000年、0001年1月、不正な月、配列、余分な空白や改行を拒否し、現在月へfallbackしない。
* 選択IDはUUIDの配列で1〜100件とし、小文字・昇順へ正規化する。
  大小文字を揃えた後に同じIDになる場合も重複として拒否する。
* requestIdは既存のUUID v4検証を利用し、小文字へ正規化する。
  previewFingerprintは64桁の16進文字列として検証し、小文字へ正規化する。
* FormDataでは選択IDだけを反復項目として許可する。
  その他の単一項目の重複、File値、未許可項目は拒否する。
  Nextが付加する$ACTION_接頭辞の輸送用項目は業務入力として利用しない。
* 入力はtargetMonth・selectedEventIds・requestId・previewFingerprintに限定する。
  clientからclubId・実行者・status・コピー日時・本文等を受け取らない。
* この検証が保証するのは入力構造だけである。
  認証・認可、前月候補への所属、fingerprintの一致、冪等性は後続粒度で保証する。

コピー列と結果の契約
* コピー列はtitle・content・genre・targetRoles・startAt・endAt・isAllDay・location・
  meetingAt・meetingLocation・belongings・notesとする。日時以外の値やnullを黙って変更しない。
* Client用previewは、ID・見出し・新旧日時・終日区分・補正項目・重複・除外理由・初期選択へ限定する。
  コピー本文や関連行、Prismaのモデル全体をClientへ返さない。
* preview結果はREADY（0件も含む）・TOO_MANY・FORBIDDEN・PREVIEW_FAILEDで区別する。
* 実行結果はCREATED・ALREADY_COMPLETED・VALIDATION_FAILED・FORBIDDEN・PREVIEW_CHANGED・
  CONFLICT・CREATE_FAILED・RESULT_UNKNOWNで区別する。
  完了結果は対象月と作成件数だけとし、本文・生Error・DBエラー原文を含めない。
* 保存後の再検証失敗は、保存済み成功データのneedsReloadで案内できる契約とする。
  入力のrequestIdだけで保存済みと判断しない。

未確定事項（提案のまま保持し、確定済み仕様として実装しない）
* 元DRAFTも対象にするか、既存完全一致候補を明示選択で複製できるか。
* 月末補正で候補同士が一致した場合の初期選択と、利用者による選択可否。
* 終了・集合が対象月の前後に跨る場合の扱い、DST fold時の時刻選択・表示。
* 不正source・DST gap・補正後の期間逆転を理由付きで選択不可にする方針。
* 秒・ミリ秒を保持する方針、初回送信後の選択変更時の再preview・requestId更新の運用。

粒度1の実装範囲
* 入力・preview・結果の型契約、入力構造検証、境界テストだけを追加する。
* 日時変換・比較・fingerprint計算・DB・Repository・Service・Action・画面は後続粒度とする。
  この粒度だけを適用しても、予定は作成されずDB変更も発生しない。
