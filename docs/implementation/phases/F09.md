F09. Platformサポート管理画面
目的
DEVELOPERまたはSUPPORTが全クラブのSupportReportを管理できるようにします。
実装範囲
1. Platform専用ログイン導線を確定する。
   - 推奨：/platform-loginを追加し、クラブMembershipが0件でもPlatformAdminならログインできるようにする。
2. requirePlatformAdmin()の存在しないredirect先を修正する。
3. /platform/supportへ専用layoutを追加し、クラブ用フッターを表示しない。
4. 全クラブのSupportReportを新着順で表示する。
5. クラブ、status、categoryで絞り込めるようにする。
6. 内容全文を安全に表示する。
7. statusをOPEN / IN_PROGRESS / ON_HOLD / RESOLVEDで変更する。
8. 内部メモを更新する。
9. handledByPlatformAdminId、statusChangedAt、resolvedAtを正しく更新する。
10. PlatformAdminがクラブのOWNER権限を自動的に得ないことを維持する。
受入条件
- isActive = falseのPlatformAdminは入れない。
- 一般クラブ会員はURL直打ち・Action直呼びの両方で拒否される。
- RESOLVEDへ変更するとresolvedAtが入り、戻すとnullになる。
- Platform画面からイベント・お知らせ等のクラブデータへ越権アクセスできない。
理解する重要箇所
- PlatformAdminとClubMembershipが別権限であること
- サポート担当者が全クラブ報告を見られる例外の境界
- Platform専用layoutとクラブlayoutを分ける理由

【追加】粒度1：管理入力・一覧・結果の契約
- ユーザー確定事項：内部メモ保存時は対応者を更新する。
- ユーザー確定事項：statusChangedAt・resolvedAtは実際のstatus変更時だけ更新する。
  同じstatusの再送は変更なしとして成功し、日時・対応者を維持する。
- 実変更でRESOLVEDへ入ると、状態変更日時と解決日時を同一のサーバー時刻にする。
  非RESOLVEDへの実変更ではresolvedAtをnullにする。メモ保存では両日時を維持する。
- ユーザー確定事項：一覧は1ページ50件。clubId・status・categoryをAND条件で絞り込む。
- 実装方針：queryは単一文字列のみ。フィルター省略・空欄は全対象、page省略は1。
  pageは1〜10000の正整数表記のみとし、不正値・配列・重複は全件取得に丸めず拒否する。
  createdAt降順・id降順のoffset方式。新規投稿によるページ間移動は保証しない。
- 実装方針：内部メモはtrim後5000 UTF-16コード単位以内。空欄はnull。
  超過分を切り捨てず拒否する。既存保存値を表示時に切り捨てない。
  オブジェクト入力の正規化済みnullも許可し、FormDataは単一文字列のみとする。
- 実装方針：reportIdはUUID、requestIdはUUID v4。いずれも認可の代用にはしない。
  expectedUpdatedAtはミリ秒付きUTC ISO表記（Date.toISOString形式）で検証する。
  更新時には最新のSupportReport.updatedAtと比較し、競合はCONFLICTとして返す。
  同じstatusでも最新権限・対象・versionの確認を省略しない。
  通知結果保存でもupdatedAtが変わり得るため、競合を無条件再試行しない。
- 実装方針：statusとメモは別入力・別更新。担当者は認可context、管理日時はサーバー由来。
  本文・snapshot・所属・クラブ・通知列を管理フォームから更新しない。
- 結果契約：一覧はFOUNDまたは固定失敗分類、更新はUPDATED/UNCHANGEDまたは固定失敗分類。
  更新結果は報告ID・versionだけを成功時に返し、本文・メモ・例外原文を返さない。
- この粒度では純粋な検証・更新方針と型だけを追加する。
  認可・Repositoryでの原子的更新・Action・画面・再検証への接続は後続粒度で実装する。
