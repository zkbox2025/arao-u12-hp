# 会員の参加リンク(共有URL・QRコード)と、数字による承認:設計

- 作成:2026-11-27(設計のみ。コード・DB・Auth・本番は変更していない)。
- 状態:**利用者(右田和也)が、2026-11-28 までに、判断事項(D1〜D5)を決定済み。J1から、実装する。**
- 粒度:F13、HP管理認可のDB化(`website-admin-db-plan.md`)、招待の修正(`invitation-existing-auth-plan.md`)とは**別の実装単位**。
- 値(メール・ID・URL・トークン・数字)は、この文書に記録しない。

## 1. 目的と利用者の決定

### 1.1 目的
OWNER が、保護者1人ずつのメールアドレスを入力して、招待メールを送る手間をなくす。
OWNER が「参加リンク(QRコードつき)」を1つ発行し、グループLINEに貼る。保護者は、自分で申請し、
OWNER が、LINEで届いた数字と照合して承認すると、会員(MEMBER)になる。承認後は、従来と同じ。

### 1.2 利用者の決定(2026-11-27)
| # | 決定 |
| --- | --- |
| 1 | 申請の入力項目は、**名前(保護者の名前)・メールアドレス・パスワード** |
| 2 | 承認できるのは、**OWNERのみ** |
| 3 | 数字の有効期間は**7日**。参加リンクの有効期限は**30日** |
| 4 | OWNERへの、新しい申請の通知は、**なし**(一覧で確認する) |
| 5 | 役割は、**MEMBER固定** |
| 6 | メール確認前(申請の送信後、確認メールのリンクを押す前)のアカウントは、**24時間**で、自動で整理する |
| 7 | 承認制(登録した人は「承認待ち」。OWNERが、1人ずつ承認する) |
| 8 | メール確認は、**する**(確認メールのリンクを、押した後に、数字を発行する) |
| 9 | D1:QRコードの生成ライブラリの追加を、**承認**(J2で追加。候補は、ライセンス・保守状況を確認して、提示する) |
| 10 | D2:リンクごとの、申請の上限は、**300件**(1クラブで、100人を超える場合を想定) |
| 11 | D3:クラブに、有効なリンクは、**1つ**。D4:登録完了メールの文面は、実装時に、案を、提示する。D5:CAPTCHAは、今回は、入れない |

### 1.3 範囲外(今回は、作らない)
- 子どもの登録(承認後に、別の画面で行う。既存の仕組みのまま)。
- OWNER以外(COACH・OFFICER)による承認。
- 申請の通知(LINE・メール)。
- CAPTCHA(申請数の制限で足りない場合に、別の粒度で追加する)。
- 他のクラブ向けの、公開の参加ページ(マルチテナント化の後)。

## 2. 全体の流れ

```
1. OWNER:管理画面で、参加リンクを発行する(QRコードつき。画面に、1回だけ表示) → グループLINEに貼る
2. 保護者:リンクを開く → 名前・メールアドレス・パスワードを入力して、送信
3. システム:確認前のAuthアカウントを作り、確認メール(Resend)を送る。申請は「メール確認待ち」
4. 保護者:メールのリンクを開く → 「登録を送信する」ボタンを押す
5. システム:メールを確認済みにする。6桁の数字を発行する。申請は「承認待ち」。数字を、保護者の画面に表示する
6. 保護者:数字を、OWNERに、LINEで送る(個別のトークを推奨)
7. OWNER:管理画面の「承認待ち」の一覧で、LINEで届いた数字と一致する申請を、承認する
8. システム:AppUser・ClubMembership(MEMBER・ACTIVE)を作る。「登録完了」のメールを送る
```

## 3. 状態

### 3.1 申請(`ClubJoinRequest`)の状態
| 状態 | 意味 | 次の状態 |
| --- | --- | --- |
| `AWAITING_EMAIL_CONFIRMATION` | 申請済み。確認メールを送った。リンクは、まだ、押されていない | `AWAITING_APPROVAL`(確認・数字の発行)、`EXPIRED`(24時間で、整理) |
| `AWAITING_APPROVAL` | メール確認済み。数字を発行済み。OWNERの承認待ち | `APPROVED`、`REJECTED`、`EXPIRED`(7日) |
| `APPROVED` | 承認済み。会員になった | (終了) |
| `REJECTED` | OWNERが、却下した | (終了) |
| `EXPIRED` | 期限切れ | (終了。再申請は、5.5) |

### 3.2 参加リンク(`ClubJoinLink`)
- クラブごとに、**有効なリンクは、1つだけ**。再発行すると、前のリンクは、無効になる。
- 状態は、`revokedAt`(無効化の日時)と、`expiresAt`(30日)で決まる。

- **既存の `ClubMembership` の状態(`INVITED` など)は、増やさない。** 申請は、専用のテーブルに持ち、承認の時に、`AppUser` と `ClubMembership`(ACTIVE)を作る。
- `ClubInvitation`(メール招待)は、変更しない。両方の方式が、共存する。

## 5. 各段階の仕様

### 5.1 参加リンクの発行・無効化(OWNER)
- 場所:管理画面の会員管理(`/club/[clubSlug]/admin/members`)に、「参加リンク」のエリアを追加する。
- Server Action:OWNERを、サーバーで、再確認する(`requireClubAppOwnerAccess`)。クライアントの `clubId` を、権限の根拠にしない。クラブは、`clubSlug` と、サーバーの認可から決める。
- 発行:`createSecureToken()` で生トークンを作り、`hashToken()` を、DBへ保存する。既存の有効なリンクは、同じトランザクションで、無効化する。
- 表示:URL(`{appBaseUrl}/club-join?clubSlug=…&token=…`)と、QRコードを、**発行の直後の1回だけ**、表示する(生トークンを、保存しないため)。再表示が必要なら、再発行する。
- 無効化:OWNERが、「このリンクを無効にする」を押す。以後、そのリンクでの申請は、できない(申請済みのものは、影響なし)。
- QRコード:URLを、画像にする。**QRコードの生成ライブラリの追加が、必要**(7章の判断事項D1)。

### 5.2 申請(保護者。未ログイン)
- 入口:`/club-join?clubSlug=…&token=…`。`proxy.ts` が、招待と同じ方式で、クエリを、短期間の Cookie(`club-join-context`)に入れ、クエリのないURLへ移す(URLに、トークンを残さない。`Referrer-Policy: no-referrer`、`no-store`)。`matcher` に、追加する。
- 画面:名前・メールアドレス・パスワードの入力。パスワードの規則は、既存の初回設定(`WelcomeForm`)と、同じにする。
- Server Action(固定メッセージのみ。生のエラー・メール・IDを、画面・ログに出さない):
  1. Cookie の文脈と、`ClubJoinLink` を検証する(存在・期限内・無効化されていない・クラブが STANDARD)。**無効なら、「参加リンクを確認できません。運営者へ、新しいリンクを、依頼してください」。**
  2. 入力を検証する(名前・メール・パスワード)。
  3. **申請数の制限**(5.6)を確認する。
  4. メールアドレスで、Authを検索する(既存の `findClubInvitationAuthUserByEmail`)。
     - **すでに、Authユーザーがいる**:新しいアカウントは、作らない。パスワードも、触らない。画面は、**新規の場合と同じ表示**(アカウントの有無を、教えない)にする。当人の宛先へ、「このメールアドレスは、登録済みです。クラブアプリへの参加は、運営者へ、ご連絡ください(招待を依頼)」というメールを送る。
     - **いない**:`supabase.auth.admin.generateLink({ type: "signup", email, password })` で、**確認前のAuthユーザー**を作る(実装時に、使用中の `@supabase/supabase-js` で、挙動を確認する)。
  5. `ClubJoinRequest`(`AWAITING_EMAIL_CONFIRMATION`、`confirmationExpiresAt` = 24時間後)を作る。
  6. 確認メールを、**Resendで**送る(Supabaseの標準のメールは、使わない)。本文には、アプリのURLの確認リンクを入れる。冪等キーを、付ける。
  7. 画面:「確認メールを送りました。メールのリンクを、開いてください(迷惑メールも、ご確認ください)」と、再送ボタン(間隔を空ける)を、表示する。
- メールの受付成功と、配送完了は、別。受付失敗の場合は、固定メッセージで、「もう一度、お試しください」と案内する。

### 5.3 メール確認と数字の発行(保護者)
- 確認メールのリンクは、アプリの `/club-join/confirm` へ移動する。**リンクを開くだけでは、何も確定しない。** 画面の「登録を送信する」ボタン(POST)を、押したときに、処理する(メールの自動スキャンが、リンクを先に開いても、数字が発行されない。既存の招待の確認(`/auth/confirm` のPOST)と、同じ考え方)。
- POST の処理(1つのトランザクションにまとめられる部分は、まとめる):
  1. トークンを検証し、メールを、確認済みにする(Authの `verifyOtp` の `signup`)。ログインのセッションも、できる。
  2. 申請が `AWAITING_EMAIL_CONFIRMATION` で、期限内であることを、確認する。
  3. 6桁の数字を、乱数で作る(暗号論的乱数)。`[clubId, verificationCode]` の部分一意制約に、衝突したら、作り直す(上限回数つき)。
  4. 申請を、`AWAITING_APPROVAL`・`emailConfirmedAt`・`codeIssuedAt`・`codeExpiresAt`(7日後)に更新する。
  5. 画面に、数字と、「この数字を、運営者へ、LINEで、送ってください(個別のトークを、おすすめします)」を、表示する。
- **冪等**:同じリンクを、もう一度、開いても、同じ数字を表示する(新しい数字は、発行しない)。
- **数字の再表示**:`/club-join/status`(ログイン後)で、自分の申請の状態と、数字を、いつでも見られる。
- 既存の、ログイン済みで、会員でない人の扱い(`/club/select` 等で、404)は、変えない。**承認前は、クラブの情報を、一切、見られない。**

### 5.4 承認・却下(OWNER)
- 場所:会員管理の画面に、「承認待ち」の一覧を追加する(名前・メール・数字・申請日時・残りの有効期間)。**メールは、OWNERだけに、表示する。**
- 承認(Server Action):
  1. OWNERを、サーバーで、再確認する。クラブは、認可から決める。`requestId` が、そのクラブの申請であることを、Repositoryで、絞って確認する。
  2. 申請が `AWAITING_APPROVAL`・数字の期限内であることを、確認する(承認画面に、LINEで届いた数字を、入力してもらう確認は、**設けない**。一覧の数字の見比べで、足りる)。
  3. Authユーザーが、存在し、メール確認済みで、申請のメールと一致することを、確認する(既存の `auth.users` の読取りを、再利用)。
  4. `Serializable` のトランザクションで、`AppUser`(なければ作る。`id` = `authUserId`、メール・名前)と `ClubMembership`(MEMBER・ACTIVE・`canManageWebsite` 偽)を、作り、申請を `APPROVED`・`membershipId`・`decidedAt`・`decidedByMembershipId` に更新する。**既存の `AppUser` は、更新しない**(`create` のみ。ID・メールの食い違いは、手動対応)。**すでに、そのクラブの会員の人は、拒否する。**
  5. 「登録完了」のメールを、Resendで、送る(ベストエフォート。失敗しても、承認は、取り消さない。失敗は、一覧に、固定表示で、残す)。
- 却下:申請を `REJECTED` にする。数字は、無効になる。Authユーザーは、削除しない。
- 二重の承認・同時の操作:`status` の条件つきの更新で、1回だけ、成功する。

### 5.5 期限切れと再申請
- 数字の期限(7日)が、過ぎた申請は、`EXPIRED` になる(Cron。5.7)。確認前のAuthユーザーの整理は、5.7。
- **再申請**:メール確認済みで、`EXPIRED`・`REJECTED` でない申請が、なくなった人は、`/club-join/status`(ログイン後)の「新しい数字を発行する」で、再申請できる(新しい申請を、作る)。**却下された人は、OWNERが、再度、承認するまで、再申請できない**(同じ画面に、固定のメッセージを、表示する)。

### 5.6 悪用の対策
| 観点 | 対策 |
| --- | --- |
| 大量の申請 | リンクごと・IPごと・メールごとの回数制限(既存の `lib/security/rate-limit.ts` と同じ考え方。ハッシュ化したIP・メールで数える。実装時に、新しい種類を追加する)。リンクごとの、承認待ち・メール確認待ちの上限(300件。7章のD2) |
| メール爆撃(他人のアドレスへの、大量の確認メール) | メールごと・IPごとの、1時間あたりの、回数制限 |
| アカウントの有無の推測 | 既存のメールでも、同じ表示。応答の内容を、そろえる |
| 他人のメールでの登録 | 確認メールが、本人に届く。本人が、ボタンを押さない限り、数字は、発行されない。数字がないと、OWNERは、LINEで、照合できない |
| リンクの漏洩 | 承認制のため、会員には、なれない。OWNERが、無効化・再発行できる。有効期限30日 |
| 数字の推測 | 数字は、認証の情報ではない(数字だけで、ログイン・参加は、できない)。承認は、OWNERの操作に限る |
| 数字の漏洩(グループに書かれた) | 他人が、数字を知っても、承認できない。個別のトークを、案内する |
| ログ・画面 | 固定メッセージ。メール・名前・数字・トークン・IDを、ログ・エラーに出さない |

### 5.7 整理(Cron)
- `/api/cron/club-join-requests`(1時間ごと。`vercel.json` に追加。**本番の設定の変更。承認が必要**)。既存の `isAuthorizedCronRequest` で、認可する。
  1. `AWAITING_EMAIL_CONFIRMATION` で、`confirmationExpiresAt` を過ぎた申請を、`EXPIRED` にし、**次の条件を、すべて満たすAuthユーザーだけを、削除する**:申請の `authUserId` と一致する/メールが未確認/`AppUser`・`ClubMembership`・`PlatformAdmin` がない/他の申請に使われていない。1つでも外れたら、削除しない(固定のログのみ)。
  2. `AWAITING_APPROVAL` で、`codeExpiresAt` を過ぎた申請を、`EXPIRED` にする(Authユーザーは、削除しない)。
- 削除の件数だけを、ログに出す。

## 6. 認可・テナント分離
- 参加リンクの発行・無効化、承認・却下は、**OWNERのみ**。サーバーで、必ず、再確認する。クライアントの `clubId` を、根拠にしない。
- Repositoryは、認可済みのクラブで、絞る。他のクラブの申請・リンクを、読み書きできない。
- 公開の入口(`/club-join`)は、未ログインで、アクセスできる。リンクの検証と、回数制限で、守る。
- HP管理の認可(`WEBSITE_ADMIN_AUTH_MODE`、`canManageWebsite`)には、**触れない**。新しい会員は、`canManageWebsite` 偽。
- Supabase Auth のユーザーは、HPの管理ログインと共用。確認前のユーザーは、HP管理に、入れない(DB方式の認可は、会員の所属が必要。`WEBSITE_ADMIN_USER_IDS` は、固定のIDのみ)。

## 9. テスト計画(実装時)
- ドメイン:数字の生成(桁数・乱数・衝突の再試行)、状態遷移の許可・拒否、期限の判定。
- Repository(使い捨てのDB):部分一意制約、複合外部キー(他クラブの結びつきの拒否)、承認の二重実行、同時の数字の発行、条件つきの更新。
- アプリケーション(AuthとResendは、mock):無効・期限切れ・無効化されたリンク、既存のメール(同じ表示)、確認前の整理の安全条件(削除しないケース)、承認時の既存会員の拒否、メール送信失敗の扱い、ログに、個人情報が出ないこと。
- 認可:OWNER以外の拒否、他のクラブのOWNERの拒否、未ログイン・確認前のアカウントのクラブ情報の拒否。
- E2E(使い捨てのローカル環境):申請 → 確認 → 数字 → 承認 → ログイン、までの一連。迷惑メール・メールの自動スキャン(リンクだけ開く)の想定。

## 10. 利用者の運用(承認後の、使い方)
