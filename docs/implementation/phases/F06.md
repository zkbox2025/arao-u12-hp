F06. /welcome・招待承諾
目的
招待された利用者が本人確認後に、招待を一回だけ承諾できるようにします。
新規アカウントは初回パスワードを設定し、既存アカウントは再設定せずログインして承諾します。
実装範囲
1. Auth confirm Routeでinviteを扱い、Supabaseセッション確立後に/welcomeへ安全に遷移する。
2. URLのraw tokenを検証後に除去し、必要なら短時間・HttpOnly・SameSite cookieへ交換する。
3. /welcomeで次を確認する。
   - token hash一致
   - 未使用
   - 有効期限内
   - Invitationが承諾可能状態
   - MembershipがINVITED
   - ログイン中Auth userと招待emailが一致
4. 新規アカウントはパスワード8文字以上・英字と数字を各1文字以上含むこと・確認一致を検証する。
   記号は禁止せず、パスワードのtrim・全角変換などは行わない。
5. 新規アカウントはSupabase Authのパスワード更新後、DB承諾処理を一回限りで実行する。
   既存アカウントは本人のログインを確認し、パスワードを更新せずDB承諾処理を実行する。
6. InvitationをACCEPTED、acceptedAt=nowへ更新する。
7. MembershipをINVITED -> ACTIVEへ更新する。
8. 二重送信・二重承諾は条件付き更新で拒否する。
9. 失効、取消、email不一致、すでに承諾済みを区別して安全な案内を表示する。
10. 完了後は対象クラブへ遷移する。
受入条件
- 有効な招待だけ承諾できる。
- tokenだけを別Authユーザーが取得しても承諾できない。
- 同時に2回送信しても一度しかACTIVEにならない。
- 承諾後のtokenは再利用できない。
- 複数クラブ所属になる場合も既存所属を壊さない。
- 既存アカウントの承諾では、パスワードを変更しない。
- フォームのActionStateにパスワード・確認値を保持せず、入力エラーにも値を含めない。
理解する重要箇所
- Supabaseの認証確認とアプリDBの招待承諾が別処理であること
- token、Auth email、Invitation emailの三者を照合する理由
- 条件付き更新による一回限り保証

粒度1の契約と後続への引き渡し
- Domainの受取人判定は、クラブ・token hash・Auth ID・正規化email・所属の対応を検査する。
  承諾可能状態・期限・INVITEDの基本判定には既存のisUsableClubInvitationを使う。
- 失効理由は本人のAuth IDと現在emailを照合した後に判定する。
  別人には招待の取消・期限切れ・承諾済みなどの詳細を返さない。
- 表示用のClubInvitationAcceptanceViewには、利用可能時のクラブ名・正規slug・期限、
  利用不可時の理由、処理失敗の区別だけを持たせる。hash・Auth ID・emailは含めない。
- 新規・既存の区別をAppUserの存在、email_confirmed_at、URLやcookieの自己申告で判断しない。
  既存ルートは検証済みのパスワード認証sessionを根拠にする。
  SDKのgetClaimsとAMRによる確認は粒度5で実証し、不明な場合はパスワードログインへ案内する。
- 粒度1の純粋関数はセッションの正当性やDB更新の成功を保証しない。
  Repositoryでの最新状態の再照合・条件付き更新、Auth・Action・画面への接続は後続粒度で行う。
