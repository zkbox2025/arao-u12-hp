# HP管理者の認可方式の切替：手順書（env → union → db）

本書は、HP管理画面の認可を、環境変数 `WEBSITE_ADMIN_USER_IDS` から、DB（`ClubMembership.canManageWebsite`）へ移す
**切替日の手順書**である。設計は `docs/implementation/phases/website-admin-db-plan.md`（以下「計画」）に従う。

- 作成：2026-11-26（手順書のみ。コード・DB・Auth・環境変数は変更していない）。
- 値（ユーザーID、メール、環境変数の値、指紋）は、記録しない。結果は、真偽値・件数・画面の種類だけを書く。
- 本番の操作（読取り、環境変数の変更、デプロイを含む）は、**操作ごとの明示承認**を得てから行う。過去の承認は、流用しない。
- 結果は、`docs/runbooks/production-migration.md` に、追記で記録する（番号は、続きから）。

## 3. 切替日の手順

### 前提の確認（作業枠の開始時）

- 準備 P1〜P6 が、すべて済んでいる。R1 が、期待どおり。
- 作業者は、旧一覧の値の控え（P6）を、手元に持っている。
- 管理者の4人（一覧の1・2・4・5番）が、作業枠の間、連絡を取れる。

### S1：`union` へ切り替える（一覧の3番の除外を含む）

1. Vercel の環境変数（Production）で、次の2つを、**1回の編集**で変更する。
   - `WEBSITE_ADMIN_USER_IDS`：**3番を除いた4人**にする。
   - `WEBSITE_ADMIN_AUTH_MODE`：`union`。
2. 再デプロイする。
3. 確認：管理者の4人が、HP管理にログインでき、主要画面が開く。

**3番の除外を、`union` と同時に行う理由：** 3番は、DBに所属がない。環境変数に残すと、`union` の間、3番がログインするたびに「環境変数は許可、DBは不許可」の食い違いが記録され、「食い違いが0」の判定ができなくなる。決定（B）のとおり、3番は HP 管理者から外す。

- **合格：** 画面が開く。**戻し：** S1 の2つの変更を戻す（§4）。

### S2：食い違いが 0 であることの確認（併用の落とし穴に注意）

- **併用の間は、環境変数が許可する人は、DBが拒否しても通る。**「入れた」ことでは、合格にならない。
- 管理者の4人が、順に、HP管理のログイン画面からログインし、主要な画面（ダッシュボード、お知らせ、FAQ、問い合わせなど）を開く。
- 判定は、**Vercel の Runtime Logs**で行う。次の文言を、時間帯を指定して検索する。
  - `判定が食い違いました` → **0件であること**。
  - `DBの判定に失敗しました` → **0件であること**。
- **Runtime Logs の保管期間は、プランで異なり、短い**（作業枠の中で、その場で確認する）。ログに、ユーザーIDやメールは、出ない設計。
- **更新の確認（計画 §3.4 の「1つ更新する」）：** 本番のHPデータを書き換えることになるため、**既定では行わない**（表示のみで判定する。認可は、ページとアクションで同じ関数を使う。アクションの拒否は、ローカルE2E（P4）で確認する）。更新を行う場合は、更新の内容を、事前に決めて、別に承認する。
- **合格：** 上の2つの文言が 0件。 **戻し：** 1件でもあれば、`env` へ戻して、中止する（§4）。

### S3：非管理者の拒否の確認

- 次の人が、HP管理のログイン画面からログインを試み、**拒否される**こと（一般的なエラーの表示。管理者登録の有無は、表示されない）。
  - 会員（MEMBER）のテスト用アカウント（本番にある、退会状態のもの）。
  - 会員でない Auth ユーザー。
- 試験用アカウントのパスワードが分からない場合は、その確認は、行わない（リセットは、実メールの送信のため、別の承認）。その場合の代替：ローカルE2E（P4）の結果で補い、本番では、**一覧に載っていない管理者以外の人**が拒否されることを、運用書に、未確認として残す。
- **合格：** 拒否される。**許可されたら、直ちに `env` へ戻す**（§4）。

### S4：`db` へ切り替える

1. `WEBSITE_ADMIN_AUTH_MODE` を `db` にする。`WEBSITE_ADMIN_USER_IDS` は、**残す**（戻しのため。削除は、§5）。
2. 再デプロイする。
3. 確認：管理者の4人が、もう一度、ログインして主要画面を開ける。S3 の人が、拒否される。
4. 食い違いの記録は、`db` では、出ない（DBのみで判定する）。代わりに、**DBの確認の失敗**は、エラー（500）になる。ログで、エラーがないことを確認する。
- **合格：** 4人が開ける。非管理者は、拒否される。**戻し：** `union` か `env` へ戻す（§4）。

### 切替日の終わりに

- 運用書へ、実施の日時、各段階の結果（合格・不合格、ログの件数）、戻しの有無を、記録する。
- 観察期間（7日）を開始する。

## 4. 戻し方

| 状況 | 戻し | 注意 |
| --- | --- | --- |
| S1・S2・S3 で不合格 | `WEBSITE_ADMIN_AUTH_MODE` を `env`（または削除）に戻し、再デプロイする。`WEBSITE_ADMIN_USER_IDS` は、**除いた3番を戻すかを、利用者が判断する**（決定（B）のとおり、通常は戻さない） | 値は、旧一覧の控え（P6）から入力する |
| S4（`db`）で不合格 | `union` か `env` へ戻し、再デプロイする | `env` へ戻すときは、**その間に取り消した権限を、旧一覧にも反映してから**戻す（取り消した人が、再び許可されるのを防ぐ） |
| 緊急（許可してはいけない人が入れる） | 直ちに、`WEBSITE_ADMIN_AUTH_MODE` を `env` に戻し、旧一覧から、その人を外して再デプロイする | 併用中は、DBの取消しだけでは、**取り消せない**。旧一覧も変更する |
| DB障害でログインできない（`db`） | `env` へ戻す | `db` では、DBが失敗すると、**許可しない**（安全側） |

- **併用中の権限の取消し：** 併用を中止して `env` に戻し、取消しを済ませてから、やり直す。

## 5. 観察期間と、旧一覧の削除

- **観察：** `db` への切替後、**7日間を目安**に、認可の問題がないことを見る。
- **削除の条件（計画 §3.5。決定）：**
  1. 期間中、認可に問題がない。
  2. DB方式で、**権限取消し後のアクセス拒否**を確認済み。確認は、P3 のスクリプトで、試験用アカウントの `canManageWebsite` を外し、拒否されることを見る（本番の書込みのため、別の承認。確認後、必要なら、付与し直す）。
  3. 戻しの手順（§4）を、確認済み。
- 削除する作業（環境変数 `WEBSITE_ADMIN_USER_IDS` の削除、`validate-env` の必須の見直し、コードの旧経路の削除）は、**別の作業**として、承認を取る。
- 削除後に `env` へ戻すことは、できない（戻しの手段が消える）。削除の前に、§4 の戻しを、1回、確認する。

## 8. 補足：P4（ローカルE2E）の範囲

- 2026-11-26 に、認可層の統合試験を追加した（`tests/website-admin-authorization.integration.test.ts`）。使い捨てのローカルDBと実物のDB確認を使い、ブラウザ・Next本体・実Authのクッキーは使わない。
- 実ブラウザのE2Eは、F12のE2E基盤（専用checkout・本番ビルド・ローカルSupabase・必須suiteの一覧と件数の照合）の拡張が要る。拡張の内容：E2Eのサーバーに `WEBSITE_ADMIN_AUTH_MODE`・`WEBSITE_ADMIN_CLUB_SLUG` を渡す、fixtureに `canManageWebsite` の所属を足す、`/admin/login` のログイン入口を足す、新しいspecを必須suiteの一覧に登録する。変更が大きいため、実施するかは、利用者の判断。
- 実ブラウザのE2Eを行わない場合の代替：切替日の S2・S3（本番での実ログインと、拒否の確認）を、ブラウザでの確認とする。
