設計書「ARAO U-12 HP」
以下「ARAO U-12 BASKETBALL CLUB」のホームページを開発・運営する。
①このHPの開発の経緯について
私の父親が今年の4月に新たに既存の2チームを統合させて立ち上げた小学生ミニバスケットクラブチームのホームページの作成と運営、保守などを手掛けたい。決断の理由としては今回の父親のクラブチームホームページ開発は、初めて人からの依頼からホームページの開発・運営まで経験できるから、フリー最新設計書ランスで働く準備として適切だと考え、設計から運営・保守までしっかりやろうと思えたためである。ちなみに、私の父親は、以前にミニバスケットボールクラブを全国大会や九州大会に導いた経験がある名監督であるため、そこをクラブの強みとしたい。

②このHPで解決できることとできること
②-1このHPで何を解決できるか：
クラブへの入会を検討している保護者にチームを知ってもらい、不安や心配、疑問を解決することで、スムーズに入会してもらうため。

②このHPでできること：
・入会を検討している保護者が「どんなチームであるか」やコーチの指導方針、活動概要、「よくある質問」を通して入会後の不安や心配を軽減させることができる
・体験/見学の申し込みができる
・チームに問い合わせができる

明文化
⚫︎下書き/公開について
管理者ページの中のFAQ管理ページ、お知らせ（練習スケジュール変更画面）ページにはContentStatusがあり、下書きと公開を選択することができる。公開なら、公開ページにて公開され、下書きなら公開されない。なお、文章ブロックはサイト上の固定文章であり、非表示にすると公開ページの一部が空欄になるため、下書き/公開切替は設けない。
管理画面で保存した内容は公開ページへ即時反映する。
⚫︎お知らせ（練習スケジュール変更画面）ページではeventDateをMVPv1.5以降はカレンダーで任意で選択でき、選択するとその日までトップページに緊急時のお知らせとして表示される（MVPv1の段階では手入力）。
⚫︎未ログイン状態で【管理者ページ】へアクセスした場合はログインページへリダイレクトする。
⚫︎管理者数: 複数管理者（コーチ3人＋開発者1人の合計4人）。
admin（管理者権限）の判定方法:将来的な一般ユーザー拡張の予定はなく、Supabase Auth（Add user）に登録されるのはこの4人のみ（＝ログイン成功者は全員管理者）となるため、特別なテーブルや .env への個別メールアドレスの許可リストの定義は行わない。 なお、プログラム側でロールの識別が必要な場合は、Supabase Authの「User Metadata」に role: "admin" を付与して判定する方針とする。
⚫︎申し込み送信後フローの流れ
入力：問い合わせ/体験見学フォームの必須項目を全て入力し、プライバシポリシーに同意する。
送信：送信ボタンを押す。なお、DB保存完了するまではdisabled(Pending)にしてボタンを押せなくする。
バリデーション（フロント側）：入力値（フォームデータ）を取得して、必須項目の質問に答えているかをチェックし、漏れがあればエラーを表示して終了。チェック成功したら成功を投げる。
バリデーション（サーバー側）：DB保存前にフロントよりもチェック項目を追加し厳しめにする（具体的には、必須チェック、文字数制限、メール形式、電話番号形式、希望日は過去でないか、第一希望日と第二希望日が同じでないかなど）
DB保存：ポスグレの該当テーブル（SessionApplicationとContact）にデータを記録する。
完了画面/モーダル：DBに保存完了したら、showSuccess = trueとし、URLの末尾に?…=,,,をつける。ページ側（ブラウザ）でサーチパラムスでURL末尾を取得し、DB保存成功を検知したら、モーダル表示を行う（トップページに戻ったら（画面遷移したら）消パラムスを削除する仕様にする）。なお、管理者および送信者への確認通知メールがエラーで落ちても、DBの保存が完了しているのであれば完了画面/モーダルは表示する。
送信者確認メール：DB保存完了したら送信者宛にメールにてフォームデータが記入された自動確認メールを送信
管理者通知：DB保存完了したら管理者宛にメールにてフォームデータが記入された自動通知メールを送信

⚫︎FAQ管理ページ（/admin/(dashboard)/faq）について
DBからFAQ一覧を取得した時点で、各FAQレコードには id が含まれている。
そのため、表示用データに変換する mapper / viewModel を作る場合でも、編集・削除などのアクションに使うために id は必ず含めておくとよい。
たとえば一覧表示用には question / category / status / sortOrder だけで足りるように見えても、編集ボタンを押したときには編集対象の id が必要になり、削除ボタンを押したときにも削除対象の id が必要になる。
また、編集フォームに渡す defaultValues として question / answer / category / status / sortOrder を持たせておくと、元の値を初期表示できる。
つまり、DB取得結果をそのままUIに渡すのではなく、FAQ一覧用の表示モデルに変換する段階で、表示に必要な値とアクションに必要な id をまとめておくと扱いやすい。



⑤-1 トップページ(/explore)
1. トップページの構成（ファーストビュー）
ヘッダーのすぐ下に、長方形のボタンを５つ等間隔に配置したメニュー（ナビゲーション）を設置します。画面サイズ（デバイス）によって、以下のようにボタンの並び順（レイアウト）が切り替わる仕様とします。
* スマホ閲覧時：押しやすさと視認性を最優先し、横3列 × 縦2段（上3つ、下2つ）で綺麗に並べる。その際、下段のボタンは左詰めにし、「4」は「1」の真下、「5」は「2」の真下に配置する（「3」の真下は空欄になります）。
* PC閲覧時：画面の大きさに合わせ、横一列（横5列）などに自動で並び順が変わる（レスポンシブデザイン）。
各長方形の中には「チーム紹介」「指導方針」、「活動概要」、「体験の流れ」、「よくある質問」の文字と、その下に横棒線がありその下にスクロールを促す下矢印記号シェブロン（∨）を配置する。なお、上のヘッダーと下のチーム紹介エリアとは横線で区切られています。
2. ページ内リンク（スムーススクロール）機能
ユーザーがその長方形ボタンをクリックすると、画面が滑らかにスクロール（スムーススクロール）し、トップページ内にある該当のコンテンツエリア（セクション）まで自動で移動します。
